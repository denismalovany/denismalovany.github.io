Case Study

FeliTalk — Online English Platform for Japanese Market

Timeline

Several months, pre-HebronSoft (freelance)

My Role

UI Designer & HTML Developer — designed and built ~90% of client-facing pages

Team

Me (UI + markup), another designer (teacher-facing portal), PM, development team for backend integration

Live Site

felitalk.com ↗

Context

FeliTalk is an online English conversation platform built for the Japanese market, connecting learners with English-speaking teachers — the majority of whom are based in Ukraine. The platform's value proposition combines professional language instruction with a premium, motivation-driven experience: carefully selected instructors, original learning materials, and a streamlined platform designed to keep learners engaged and coming back.

By the time I joined, the project already had a foundation in place: the previous designer and PM had worked closely with the client to define requirements, user flows, and wireframes. I received these as structured documentation — plus a starter design system consisting of core components (buttons, layouts) and a handful of completed pages that served as visual references.

My job was to take that foundation and build the rest of the platform from it — designing and hand-coding the pages that learners would interact with every day. This wasn't a greenfield design; it was a disciplined exercise in scaling a partial design system into a complete, production-ready portal while maintaining visual coherence and technical quality across every screen.

Approach

1. Design System Onboarding

I started by thoroughly absorbing the existing design system — the component library, spacing rules, typographic scale, and color palette established by the previous designer. Rather than reinventing, my job was to extend: understand the logic behind each design decision well enough to apply it consistently to entirely new pages without breaking the visual language. The few completed pages served as north stars — reference implementations I could measure every new screen against.

2. Page-by-Page Design & Implementation

Working from the PM's wireframes and specifications, I designed and hand-coded each new page — approximately 20 unique page templates covering registration, lesson booking, teacher browsing, pricing, and the user dashboard. Subsequent pages reused these templates and their components, maintaining a consistent rhythm across the platform. Every design decision I made was immediately validated through code — I saw within minutes whether a layout worked at real screen sizes and in real browsers.

3. Japanese Typography & Layout Adaptation

This was my first experience designing for Japanese text — and it surfaced a challenge I hadn't anticipated. Simply replacing English placeholder text with Japanese kanji and kana broke layouts everywhere. Japanese characters need more visual space to be legible; what looked clean and spacious in Latin script became cramped and unreadable. I had to adjust font sizes, line heights, and container widths across the entire platform to accommodate the new script — a hands-on lesson in how typography changes across writing systems, and why localization isn't just translation.

4. Git-Based Delivery & Integration

My workflow was straightforward: pull the project from the dev branch, build locally, design and code the new pages, then push back to dev. When the frontend developers needed to integrate my markup into the backend, any questions or adjustments were handled through the same git flow — no handoff documents, no ambiguity, just working code in the repository. If something didn't look right after integration, I fixed it in the source and pushed the update.

5. Developer Collaboration — Technical Fluency in Practice

My background as an HTML developer didn't just help me code faster — it fundamentally changed how I collaborated with the development team. When backend developers flagged a feature as "complex" or "time-consuming," I could assess the claim from a position of knowledge rather than trust. I understood what was technically involved, could estimate realistic effort, and in several cases suggested simpler implementation approaches. This turned potential bottlenecks into quick, fact-based conversations — and it's a skill that carried forward into every project I've worked on since.

Result

I delivered approximately 90% of the client-facing platform — roughly 20 unique page templates that scaled through component reuse across the entire user journey. The site launched successfully and remains live today at felitalk.com, serving Japanese learners connecting with English teachers.

The design system I helped extend became the visual backbone of the platform — every new page felt like part of the same product, regardless of whether it was built from the original designer's templates or from my extensions. The Japanese typography adjustments I made ensured the platform was genuinely usable for its target audience, not just a Latin-script design with translated text dropped in.

On a personal level, this project marked my transition from pure HTML developer to UI designer. It was the bridge: I came in with deep technical knowledge and left with a design system I could point to, Japanese-market experience, and a working method — design with implementation awareness — that would define how I approached every project after.

Key Takeaways

  • Designing with implementation awareness reduces friction. Knowing how your designs will be built — the HTML structure, the CSS constraints, the browser quirks — means you design things that are not just beautiful, but buildable. Every decision carries an implicit estimate of effort.
  • Technical fluency is leverage in developer conversations. When a developer says something is difficult, being able to assess that claim from real technical knowledge — not trust — changes the dynamic. It turns negotiations into collaborations.
  • Design systems are force multipliers for multi-page products. With ~20 unique page templates, component reuse and a shared visual language weren't luxuries — they were the only way to maintain speed and coherence across the project.
  • Typography doesn't translate — it needs to be redesigned. Moving from Latin to Japanese script required rethinking font sizes, line heights, and container dimensions across the entire platform. Localization starts with legibility.
  • Transitions happen in the work. This project was my bridge from developer to designer — and the fact that I could do both on the same project meant the transition was practical, not theoretical. I proved to myself that I could design.

My Role

UI Designer & HTML Developer — design system onboarding and extension, page-by-page UI design across ~20 unique templates, hand-coded HTML/CSS markup for ~90% of client-facing pages, Japanese typography and layout adaptation, git-based delivery to development team, technical collaboration with backend developers including effort estimation and implementation guidance.
